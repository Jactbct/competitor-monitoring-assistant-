# 运维手册（单人版）

> 目标：半夜被叫起来时，能在 10 分钟内判断「哪儿坏了、怎么先止血」。
> 设计上刻意只留两种观测入口：**一封每日自检邮件** 和 **一个 `/ops/health` 页面**。

## 一、每天要看的三件事

| # | 看什么 | 正常值 | 异常含义 |
|---|---|---|---|
| 1 | 每日 09:00 自检邮件 | 采集异常率 < 2%、队列积压 0、降级率 < 15% | 异常率飙升 → 页面改版或被限流；降级率高 → prompt/模型/数据源有问题 |
| 2 | 工作台 P0 卡片数量 | 与业务预期相符 | 突然为 0 且连续数小时 → 可能采集静默失效（见「沉默告警」） |
| 3 | `/ops/health` 越权拦截数 | 0 | **>0 立即按 P0 处理**：有请求试图跨租户，或某处漏写租户过滤 |

## 二、单点故障处置（对应架构文档 §8.2）

| 单点 | 现象 | 先做什么 | 目标 |
|---|---|---|---|
| 云主机 | 全站 5xx / 探针告警 | 冷备机起 `docker compose up -d` + 恢复最近快照 | RTO 4h / RPO 24h |
| PostgreSQL | 全站 500，`/health` 返回 503 | 恢复快照；有 WAL 归档可做 PITR | RTO 2h |
| LLM 供应商 | 建议生成停、日志 `llm.failed` | ① 切备用供应商（同 OpenAI 协议，只改 base_url/key）② 直接设 `LLM_MODE=off` 跑规则模式 | ≤10 分钟 |
| 企微 webhook | 推送不出 | 自动降级邮件 → 站内；检查 webhook 是否被移出群 | 即时 |
| 采集出口 IP | 429 持续、熔断目标增多 | **不要换 IP 硬刚**；降 `COLLECTOR_QPS`、等解封或走商务申诉 | 人工 ≤24h |
| worker 进程 | 队列只增不减 | `docker compose restart worker`；`reclaim_stale` 会自动回收卡在 running 的任务 | ≤1 分钟 |

## 三、常见故障 → 排查路径

**1. 页面改版（最可能发生）**
- 现象：某类目异常率骤升，`abnormal_type=STRUCTURE_CHANGED`
- 排查：`python manage.py shell` → `from domain.extract.rules import extract`，拿最近的原始页跑一遍，看 `strong_hits`
- 处理：改 `STRONG_MARKERS` 或正则 → 跑 `pytest tests/eval/test_gate.py` → 发布
- 要求：从告警到修复上线 ≤4 小时（S-6）

**2. 到手价不准**
- 先看 `price_detail.lines`：是规则没解析出来，还是叠加逻辑判断错
- 用 `tests/fixtures/pages/` 加一个该场景的样本页，**先写失败测试再改代码**
- 发布前必须跑评测：`pytest tests/eval/ -q`

**3. 队列积压**
```sql
-- 一眼看全貌（这就是不用 Celery 的好处）
SELECT kind, state, count(*) FROM shared_job GROUP BY kind, state ORDER BY 3 DESC;
SELECT id, kind, attempts, last_error, run_after FROM shared_job WHERE state='dead' LIMIT 20;
```
- 死信 → 看 `last_error`；修完后把 `state` 改回 `pending` 即可重放（任务表就是队列）

**4. LLM 成本异常**
```sql
SELECT day, sum(value) FROM metric_daily WHERE metric='llm_tokens' GROUP BY day ORDER BY day DESC LIMIT 7;
```
- 突增通常是「变化事件暴增」（页面改版导致 diff 全变）→ 先看 `change_events` 曲线
- 硬闸：`LLM_DAILY_TOKEN_QUOTA` 用尽即降级，不会继续烧

**5. 越权拦截 >0**
- 查审计：`SELECT created_at, actor, detail FROM audit_log WHERE action='tenant.cross_access_blocked' ORDER BY created_at DESC LIMIT 20;`（需在租户上下文或 worker 账号下）
- 三种可能：用户在猜 ID（正常拦截）、代码漏写租户过滤（修代码）、RLS 未生效（检查 `FORCE ROW LEVEL SECURITY` 是否在）

**6. 模型调用失败**
- 先跑 `python manage.py llm_check`：它会打印当前 base_url / Key 长度 / 模型名，并真调一次
- 401/403 → Key 错或无权；404 → base_url 少了 `/v1` 或模型名不存在（`--list-models` 查清单）
- 400 提到 `response_format` → 网关不完整支持 JSON 模式（客户端已自动去掉该字段重试一次）
- 注意：缺 Key 不会让系统挂掉，会**确定性降级**到规则模式（卡片仍完整，只是归因粗），
  但降级率会升到 100%，`/ops/health` 与 `gate_report` 都能看到

**7. 磁盘涨得快**
- 先分清楚是谁在涨：`/ops/health` 的「数据体积与保留期」卡片直接给出每张表的大小
- 原始页（`.data/raw`）：7 天自动清理，若没降说明清理任务没跑（看每日自检邮件里的「清理」一行）
- 快照表：400 天保留；若行数逼近 2,000 万或单表 50 GB，按 `docs/adr/005-snapshot-partitioning.md` 做月分区，
  **不要**临时缩短保留期（会破坏同比分析的可比性，且用户会拿这个问「为什么数据少了」）

**8. 沉默告警（6 小时零变化事件）**
- 有活跃目标但 `change_events` 为 0 → 先怀疑解析失效，而不是「竞品都没动」
- 手动跑一次：`python manage.py shell -c "from jobs.handlers.collect import handle_collect; print(handle_collect({'target_id': 1}))"`

## 三·五、每次改隔离相关代码后必跑

```bash
python scripts/verify_pg_rls.py     # 期望 8/8
```

必须用真实角色连真库。用超级用户跑 pytest 时 RLS 会被绕过，
「测试全绿但隔离是坏的」是最容易发生的假绿。

顺便记住两个只在真库暴露的陷阱（都已修，写在这里防止回归）：

- `ALTER DEFAULT PRIVILEGES` 只按**建表时**所在 schema 记账；表搬 schema 后权限跟着表走 →
  共享层只读必须显式 `REVOKE`（`shared/0004_shared_readonly_grants`）
- 登录成功/失败会写审计，而那时租户上下文可能还没建立 → RLS `WITH CHECK` 会拒
  （`tenancy/services.audit` 已显式处理，并保证审计写失败不连坐业务请求）

## 四、发布与回滚

```bash
# 1. 备份（失败即中止）
docker compose exec db pg_dump -U postgres competitor | gzip > backup-$(date +%F-%H%M).sql.gz

# 2. 迁移 + 重启（init 服务会跑 migrate）
docker compose up -d --build

# 3. 冒烟：登录 / 工作台 / 监控列表 / 建议详情 / health
curl -fsS http://127.0.0.1:8000/health

# 4. 回滚（镜像回退；DB 只在破坏性迁移时恢复快照）
docker compose up -d --force-recreate web worker
```

**破坏性迁移必须拆三个版本**：加列 → 双写 → 切读 → 删旧列。禁止一条迁移里同时加列和删列。

## 五、恢复演练（每月一次，记录实测 RTO）

1. 新机器 `git clone` + `docker compose up -d db`
2. `gunzip -c backup-xxx.sql.gz | docker compose exec -T db psql -U postgres competitor`
3. `docker compose up -d`（init 会补齐 schema 与静态文件）
4. 校验：登录、工作台数字、最近快照时间、队列状态
5. 记录实测耗时；**超过 4 小时就升级为双机方案**（对外 SLA 只承诺 99.5%）

## 六、日志与指标在哪

| 内容 | 位置 |
|---|---|
| 结构化日志（JSON，带 trace_id） | `docker compose logs -f web worker` |
| 请求级排障 | 响应头 `X-Request-Id` = 日志里的 `trace_id` |
| 小时指标 | 表 `metric_daily`（`/ops/health` 直接读） |
| 原始页（7 天，仅排障） | `.data/raw/年/月/target_id/*.html.gz` |
| 审计（180 天） | 表 `audit_log` |
| 队列全貌 | 表 `shared_job` |

## 七、日常维护动作

| 频率 | 动作 |
|---|---|
| 每日 | 看自检邮件；处理 P0；清死信 |
| 每周 | 抽检 20 条到手价；看采纳率与降级率；跑一次真实抽样评测 |
| 每月 | 恢复演练；检查磁盘（原始页 7 天、快照 400 天应自动清理）；`/ops/health` 看表体积是否接近 2,000 万行；复核采集异常类型 Top3 |
| 每季 | 复核 QPS 预算与套餐配额；清理过期租户数据 |
