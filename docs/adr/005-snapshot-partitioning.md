# ADR-005：快照先做保留期 + BRIN，暂不做月分区

- 日期：2026-10-22
- 状态：已接受
- 影响：`shared/maintenance.py`、`shared/migrations/0005_brin_indexes.py`、`/ops/health`

## 背景

架构文档 §6.3 写的是「快照表按月分区，主键 `(id, captured_at)`」。这一条在实现时被推迟，
理由是当时没有真实数据量。现在有了实测口径：

| 项 | 数值 |
|---|---|
| 出口预算 | 1 QPS（合规上限，且是配置项，不可在线调） |
| 日快照上限 | 86,400 行（实际远低于此，目标数决定；演示租户 3 个目标） |
| 变化率 | 原型实测约 8%（只有变化才进分析） |
| 400 天保留 | 按 3 个核心目标 × 2 小时 → 约 5,256 行/年/目标 |

真实业务里一个租户 100 个目标、按 2 小时采，一年约 43.8 万行；100 个租户才 4,380 万行。
也就是说：**分区要到「几百个租户」才真正需要**，而那时瓶颈先出现在 LLM 成本而不是这张表。

## 决策

1. **不做分区**，改为三件事：
   - `SNAPSHOT_RETENTION_DAYS`（默认 400）按批清理快照与变化事件（`shared/maintenance.py`）
   - `captured_at` / `detected_at` 建 **BRIN** 索引（`pages_per_range=32`），索引体积约为 B-tree 的 1%
   - `/ops/health` 直接显示每张表的行数与体积，并在超过阈值时写出「该做分区了」
2. **触发阈值写死在这里**，到了就按下面的预案执行，不再讨论：
   - `shared.snapshot` 行数 > **2,000 万**，或总大小 > **50 GB**，或单次保留期清理耗时 > 30 分钟。

## 分区预案（到时照做）

1. 模型改为 `managed = False` + 手写 DDL 建分区父表（PG 声明式分区，`PARTITION BY RANGE (captured_at)`）；
2. 主键改为 `(id, captured_at)` 复合主键（Django 5.2 的 `CompositePrimaryKey` 可用，但会牵动外键与序列，必须单独迁移）；
3. 用「新表双写 → 回填 → 切换读 → 删旧表」四步走，禁止一条迁移里完成；
4. 分区维护任务：每月提前建下个月分区，并 `DETACH` 掉超过保留期的分区（比逐行 DELETE 快两个数量级）；
5. 切换前必须先在 PG 上跑 `scripts/verify_pg_rls.py` 与全量 pytest（分区表的 RLS 行为需要复核）。

## 后果

- ✅ 现在不付分区带来的复杂度（复合主键、手写 DDL、迁移风险）
- ✅ 磁盘与索引体积可控，清理是批量的、可中断的
- ⚠️ 保留期一过，老建议卡里的 `evidence_id` 查不回快照详情；卡片里存的**引文文本仍在**，
  所以结论与证据仍可读 —— 这是有意的取舍（400 天窗口）
- ⚠️ 单表在 2,000 万行以内仍然要盯 autovacuum：批量删除比逐行删好，但仍会产生死元组

## 反对意见

「文档里写了分区，就该照做。」——文档写的是目标形态，不是当期动作。
在数据量差两个数量级时先做分区，等于用最贵的复杂度买一个还不会发生的收益；
写清触发阈值与预案，比提前实现更能保证三年后这套东西还维护得动。
